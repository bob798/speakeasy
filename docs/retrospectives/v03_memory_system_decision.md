# V0.3 记忆系统决策文档
> 日期：2026-03-16
> 状态：已决策，待实施
> 背景：对 V0.3 记忆模块方案进行了深度复盘，否决 mem0，确定三层 SQLite 方案

---

## 一、方案沟通的项目级复盘

### 做得好的地方

**场景发散质量高**

五个维度覆盖了英语学习记忆的主要关注点。"记忆服务于什么"（三个出口：聊天内容 / 学习建议 / 学习计划）是正确的思考方向——先问"用在哪"而不是"存什么"。

**差异化定位准确**

现有学习应用只记"知识状态"，没有认真做"用户关系"。Speakeasy 的机会在此。

### 沟通的问题

**问题 1：结论跳跃，推理链断裂**

```
实际路径：
"有哪些记忆需求？" → [发散] → "mem0 很好" → "V0.3 应该引入 mem0"

缺失环节：
"V0.3 具体要交付什么用户价值？" → "交付这个价值需要什么最小记忆能力？"
```

结果是用"未来的完整愿景"驱动了"当前版本的技术选型"。

**问题 2：用最理想场景论证方案**

mem0 的价值论证基于"10 次对话后、提取准确"的前提，用最好的 case 代替了典型场景。

**问题 3：没有讨论替代方案**

没有认真评估过"不用 mem0，更简单的方式能覆盖多少场景"。

**问题 4：五个维度没有对 V0.3 裁剪**

五个维度是完整愿景，V0.3 需要的是其中的最小子集。

### 根本模式

> 发散产生愿景 → 愿景产生冲动 → 冲动跳过约束直接选型

"当前版本驱动"是对抗这个模式最有效的锚。

## 二、记忆场景的深度思考

### 按时间尺度分层

```
短期（当前 session）
  → 已有：messages 表的 conversation history
  → 无需新增

中期（最近 N 次 session，跨会话）
  → 最有价值的记忆层，"Alex 记得我"的核心来源
  → 数据量小：几十条事实

长期（累积半年以上）
  → 稳定的用户画像 + 能力趋势
  → 结构化数据，不需要向量检索
```

### 五个维度的重新审视

| 维度 | 时间层 | 数据性质 | 实际需要的技术 |
|---|---|---|---|
| 1. 语言能力（CEFR、强弱项） | 长期 | 结构化 | SQLite 表 |
| 2. 用户画像（职业、偏好、目标） | 长期 | 结构化 | SQLite 表 |
| 3. 学习行为（追问记录、FSRS 结果） | 中期 | 半结构化 | SQLite + 简单标签 |
| 4. 对话内容（事件、人物、情绪） | 中期 | **非结构化** | **LLM 提取 + 文本检索** |
| 5. 学习节奏（打卡、完成进度） | 中/长期 | 结构化 | SQLite 计数/时间字段 |

**关键发现：只有维度 4 是真正非结构化的，其余四个维度用 SQLite 足够。**

### 维度 4 的真实规模估算

```
每天练习一次，每次提取 3 条事实：
  1 个月 =   90 条
  3 个月 =  270 条
  1 年   = ~1000 条
```

在这个规模下，`text + time` 检索和语义向量检索的差距极小，1000 条内关键词过滤已能覆盖绝大多数场景。

## 三、V0.3 记忆方案

### 对照 Roadmap 的最小需求

V0.3 Roadmap：Level 评估 + 用户偏好设置 + 记忆管理页面

```
Level 评估
  → 一次性问卷 + LLM 打分 → user_profile.cefr_level
  → 纯结构化，SQLite 完成

用户偏好
  → 话题偏好、学习目标、风格 → user_profile 表 JSON 字段
  → 表单保存，注入 system prompt

记忆管理页面
  → 展示 grammar_cards（已有）
  → 新增：展示用户画像信息
```

**结论：V0.3 不需要向量检索。**

### 推荐方案：三层结构

```
层 1：user_profile 表（结构化画像）
  字段：cefr_level, profession, topic_prefs (JSON), learning_goal, personality_notes
  写入：用户填写表单时
  使用：每次对话注入 system prompt

层 2：user_facts 表（LLM 提取的中期记忆）
  字段：user_id, fact TEXT, tags TEXT, created_at, source_session_id
  写入：每次 /chat/summary 后，LLM 从对话提取 2-3 条事实
  使用：最近 20 条 + tags 过滤，注入 system prompt
  检索：text + time，无需向量

层 3：grammar_cards 表（已有）
  V0.2b 已完成，FSRS 调度，继续沿用
```

### 升级触发条件

当以下条件同时满足时，再评估引入向量检索（sqlite-vec 或 mem0）：
- `user_facts` 积累超过 500 条
- 出现检索漏网的用户反馈
- 用户规模增长到值得增加基础设施复杂度

## 四、技术方案评估原则

针对 Speakeasy 当前阶段（小团队、单用户验证期、快速迭代）：

| # | 原则 | 核心问题 |
|---|---|---|
| 1 | **当前版本驱动** | V0.x 的用户故事能验证这个方案吗？ |
| 2 | **栈内优先** | 现有栈内能解决吗？不引入新基础设施 |
| 3 | **可逃跑性** | 3 个月后能无痛迁移到其他方案吗？ |
| 4 | **可观测性优先** | 5 分钟内能解释"AI 为什么说了这句话"吗？ |
| 5 | **价值比例** | 复杂度与用户价值成比例，不与技术酷炫程度成比例 |

---

## 五、技术方案评估结果

### mem0

| 原则 | 结果 | 说明 |
|---|---|---|
| 当前版本驱动 | ❌ | V0.3 三个功能不需要它 |
| 栈内优先 | ❌ | 外部服务或自建 Qdrant，超出现有栈 |
| 可逃跑性 | ⚠️ | 专有格式有锁定风险 |
| 可观测性 | ⚠️ | 提取过程黑盒，结果可查但推理不透明 |
| 价值比例 | ❌ | 当前数据规模不足以发挥向量检索优势 |

**结论：V0.3 不引入。V1.0 后用户增长、对话积累后可重新评估。**

### sqlite-vec

| 原则 | 结果 | 说明 |
|---|---|---|
| 当前版本驱动 | ❌ | V0.3 不需要向量检索 |
| 栈内优先 | ✅ | SQLite 扩展，无额外服务 |
| 可逃跑性 | ✅ | 数据仍在 SQLite |
| 可观测性 | ✅ | 可直接查 DB |
| 价值比例 | ⚠️ | 现有规模下 text 检索已够用 |

**结论：技术本身无问题，时机未到。作为 V0.4+ 备选保留。**

### 推荐方案（user_profile + user_facts + SQLite）

| 原则 | 结果 | 说明 |
|---|---|---|
| 当前版本驱动 | ✅ | 直接交付 Level 评估 + 偏好设置 |
| 栈内优先 | ✅ | 纯 SQLite + 一次 LLM 提取调用 |
| 可逃跑性 | ✅ | 通用文本表，随时可加向量索引 |
| 可观测性 | ✅ | 每条 fact 有 source_session_id 可追溯 |
| 价值比例 | ✅ | 两张表 + ~200 行代码，覆盖 80% 记忆体验 |

**结论：V0.3 正确选型，五项全绿。**

## 总结

```
沟通问题  愿景正确，但用完整愿景驱动了当前版本选型
场景判断  五个维度中，只有维度 4 需要 LLM 提取，其余均结构化
V0.3 方案 user_profile + user_facts（LLM 提取）+ grammar_cards
评估原则  当前版本驱动 > 栈内优先 > 可逃跑 > 可观测 > 价值比例
方案结论  推荐方案五项全绿；mem0 三红否决；sqlite-vec 时机未到
```
